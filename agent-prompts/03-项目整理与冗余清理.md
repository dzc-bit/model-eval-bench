# 任务：项目整理——清冗余、统一口径、让项目对自己人友好

你是项目整理负责人。这个仓库是一个本地模型评测台，功能是对的，但**整体过于混乱**：
文档口径分叉、历史脚本堆积、巨型文件、死代码。你的任务是从「一个新人打开这个仓库能不能
快速看懂」的角度出发，把项目整理干净。

**前提**：这个任务在前端重构（另一个 agent）完成之后才开始。开始前先 `git log` 和
`git status` 看清当前状态，在最新代码上动手。

## 开工前必读（按顺序）

1. `AGENTS.md` —— 维护纪律全书，尤其「删除语义」「验证门禁」。
2. `README.md`、`设计文档.md`、`packs/core/README.md` —— 三份规则文档。
3. `console/harness/NOTES.md`、`console/harness/VALIDATION.md`（如存在）。
4. 整个目录树走一遍，建立「每个目录是干什么的」的全图。

## 要做的事（按优先级）

### 1. 冗余与死代码清理

- 前后端死代码：没人调的函数、被 if(false) 掉的逻辑、注释掉的大段旧实现、
  已被取代的兼容分支（比如 `run.drive` 盘符沙箱退役后残留的只为兼容的代码——
  注意：字段兼容要保留，逻辑死路要删，分不清的列进报告别删）。
- 重复逻辑：同一件事在两处各写一遍的（前后端各自实现同一口径、工具函数重复定义等），
  收敛到一处。
- 巨型文件拆分：单文件大到一个人读不完的（如重构后仍有的话）按职责拆开。

### 2. 历史脚本与遗物归置

- `runs/blind/tools/author_t0*.py` 是含绝对路径的历史存档。判断：还在用的留下并修好
  路径问题；纯存档的归到一个明确的 `archive/` 目录或删除（有 git 历史兜底）。
- 根目录、`runs/`、`sandboxes/` 下的临时产物、过期报告、一次性脚本，逐个判断去留。
  `runs/blind/tools/tidy_workspace.py --dry-run` 是现成的整理工具，先用它看一遍。

### 3. 口径与文档统一

- 三份规则文档（README / 设计文档 / packs README）之间、文档与代码之间的矛盾，
  逐条列出；明显是文档过期的直接改文档，明显是实现错的列出来交给我拍板。
- 同一概念在 UI 文案、API 字段、文档里叫法不一的（比如「校验/评分/判分」），
  统一成一套词，UI 文案优先向用户视角靠拢。
- `AGENTS.md` 里「待拍板 / 已知未修」一节如果有的条目已被解决，更新掉。

### 4. 新人动线

- 假设一个新人（未来的用户自己）三个月后回来：从 README 出发，能不能 10 分钟内
  知道怎么启动、怎么出题、怎么评测、出问题了看哪？把这条动线走一遍，卡点修掉。

## 硬纪律（不可违反）

- **`runs/` 下的运行记录数据一律不动**：`chat.jsonl`、`epochs/`、`report*.json`、
  `diff.patch` 等都是证据。整理只动「脚本和临时产物」，不碰「记录」。
  分不清是产物还是记录的，一律当记录，列进报告。
- `sandboxes/.snapshots/` 是受测仓库基线缓存，别的 run 还要用，**不动**。
- `packs/` 默认只读。发现题包问题写进报告，不改。
- 删除任何被 git 跟踪的文件相对安全（有历史兜底），但删除前仍要确认没有入口引用它；
  未被跟踪的目录（`runs/`、`sandboxes/` 下）删除要极其保守，宁可列进报告让我删。
- 删除语义的三个动作、门禁逻辑、`util.path_within` 这类安全边界，**不许为了「简洁」去动**。
- Windows 环境：PowerShell 用 `pwsh`；`du`/`cp -r` 进 `runs/` 会挂 junction，只按文件名拷。

```bash
python console/harness/selfcheck.py          # 0 错误 0 提示
# 每个前端 .js 复制成 .mjs 后 node --check（按当时实际数量全过）
```

- 8899 唯一实例：重启服务前扫所有 `runs/*/*/*/chat.jsonl` mtime，在飞的不重启。
