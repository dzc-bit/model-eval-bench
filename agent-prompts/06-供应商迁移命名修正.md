# 任务：修正供应商迁移命名——从端点推导名字，不从老档案 id

你是配置迁移负责人。仓库 <仓库根目录>。先读 `console/harness/config.py` 的
`_providers_from_legacy_models`（读时迁移）、`runs.py` 的 `delete_provider` 与密钥候选链
（`_key_owner_candidates` / `chat.key_status`）、`console/static/js/views/models.js` 的编辑表单。

## 问题

旧配置是平铺的 `models` 数组，读时迁移按 `base_url` 分组成供应商。现在供应商的 id/显示名
取自**第一个老档案的 id**（本机实例：两个模型被归到一个叫 `hunyuan4preview` 的供应商下，
但它实际是 cbcn 中转）——语义错误，用户不手动改就一直顶着错名字。

## 修复思路（按这个做）

1. **迁移命名改为从端点推导**：由 `base_url` 生成稳定、可读的供应商名：
   - 真实厂商：取域名核心段（如 `api.deepseek.com` → `deepseek`）；
   - 本机/内网中转（127.0.0.1、localhost、私网 IP）：用 host+端口派生（如 `local-20128`），
     并在 display_name 上明确这是本机中转；
   - 同名冲突加短后缀消解；同一 endpoint 多次迁移必须得到同一个名字（幂等）。
2. **密钥不能断**：迁移后 provider id 变了，但 `keys.local.json` 里按老派生 id 存的密钥
   必须仍能找到——核实 `chat.key_status` 的候选链是否覆盖老 id（含 legacy_ids），不覆盖就补。
   验收标准：本机现存老配置迁移后，模型档案页供应商卡仍显示「✓ 已存密钥」。
3. **记录归属不受影响**：`legacy_ids` 照旧记录老档案 id，记分板归属不变
   （另有 agent 在做身份归并，你别动 runs 统计侧）。
4. **已保存为新结构的配置（`providers` 数组）不再走迁移**，本次只修迁移路径；
   已迁移保存过的配置不二次改名（改的是推导规则，不回写存量）。
5. display_name 保持可编辑（编辑表单已支持的话确认一下；不支持就补「显示名」字段）。

## 验证

- 新增/更新测试：老平铺配置迁移后供应商名来自端点而非老档案 id；同一 endpoint 幂等；
  密钥候选链覆盖老 id；`providers` 新结构不被迁移触碰。
- 门禁：`EVAL_PYTEST_TMP=<全新临时目录> python -m pytest console/harness/tests -q` 全绿；
  `python console/harness/selfcheck.py` 0 错误 0 提示。

  扫 `runs/*/*/*/chat.jsonl` 的 mtime，最近 1–2 分钟有写入就别重启）：模型档案页供应商卡
  显示新推导的名字、密钥状态仍 ✓、两个模型仍在卡下、迁移提示条仍正常。
