必须同时成立的表述：

1. 休市安排要收口：要么只有一个权威来源，要么各副本逐条一致并有跨端校验兜底——
   任何"各自维护、偶尔同步"的状态都不合格。
2. "某天是否交易日"在所有出口（覆盖名单、页面提示、默认窗口落点）必须同源同答案。
3. 默认窗口的两端必须先落到真实交易日、再往回数窗口；不允许把任意给定日期直接
   当窗口末端，也不允许只修其中一个入口。
4. 对表外年份，宁可明确提示"超出已知的休市安排"，也不得静默当作全年无休。

已被否决的思路（不要重提）：

- "把两边的表各自手工补齐就算修好"——补齐只是又一次手工镜像，下次更新还会漂移；
  补数据可以，但必须同时把"以后不再漂移"的机制立起来。
- "覆盖检查遇到春节附近就跳过"——把问题藏进特判，换个假期照样犯。
- "把默认窗口的回退去掉，让上层自己裁"——落点校验就是防线本身，不是冗余。

## 必须同时成立的不变量

1. 权威单一：判定标准是"系统里只有一处能回答某天是否开市，其余各处都从它取数"，而不是"两份安排碰巧抄得一样"。只要还有第二处能独立作答，就还没有修完。
2. 全出口同源：判定标准是"覆盖名单、页面提示、默认窗口的落点对同一天给出的是同一个结论"，而不是"大多数日子能对上、个别日子靠人工解释"。
3. 窗口两端先落地：判定标准是"默认窗口的两端都先落到真实交易日、再以它为边界往回数"，而不是"把给定日期原样当边界、由调用方自己兜住"。
4. 连休与调休如实记录：判定标准是"整段连休连同被调换出来的上班日都照原样记下，跨月跨年的连休不被截断"，而不是"只记法定当天、把调休日留给各处自行推测"。
5. 表外年份明确说不知道：判定标准是"超出已记录范围时明确告知无法判断，并且不生成任何缺失名单"，而不是"静默按全年开市处理"。
6. 派生与缓存同生共死：判定标准是"任何派生的名单、计数、内存里的缓存都跟着权威来源一起更新，或者干脆不留缓存"，而不是"各存一份、等到下次重启才可能对上"。
7. 相邻年份互不串味：判定标准是"边界相邻的两个年份各自保留自己的安排，跨年查询时两边都正确"，而不是"把相邻年份拉平对齐"。

## 已被否决的思路（这些方向试过，不要再提）

1. "把两份安排用脚本定期同步一次"——定时同步只是把"不一致"从一直存在推迟到下一次同步之前，同步间隔里照样各答各的；而且没有一处能回答"现在这份是不是最新的"。
2. "让覆盖检查遇到对不上的年份就报错停下"——把一个静默的错误换成一次响亮的失败，用户拿不到任何可用的覆盖结论，问题本身一点没动。
3. "把休市安排改成人工在页面上按年维护"——把一致性交给人的记性，放假安排一年调整一次，漏改一次就全校错；而且维护入口没有校验，改错了也没人发现。
4. "把表外年份统一按全年开市处理，免得报错"——静默给出一个确定但错误的答案，正是现在最坑人的那种表现。
5. "干脆禁止跨年查询，绕开元旦前后的麻烦"——把可用功能砍掉换安静，验收要求里的跨年默认窗口直接就不成立了。
