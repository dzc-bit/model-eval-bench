# T2-04 参考解说明

> 本文件**只进 `reference/`**，永远不进沙箱快照白名单（§4.2 答案隔离）。
> 它是出题侧的存档：锚解为什么这么写、陷阱在哪、§6.5 逐条怎么打勾。

## 一、锚解的形态：一条协议，四个出口

§6.3 对中级题的硬性规格是"**修复需设计机制或协议**"。本题的机制就是一句话：

> **0 行日不是横截面证据。**
> 按交易日历补出来的 0 表示"没有数据"，不是"观测到的行数是零"。它不进入中位数、
> 不影响门槛；但它也不是"市场正常日"，落在它上面的缺行仍然算可行动。

锚解把这条协议收回**共享纯函数的调用约定**上：

| 出口 | 锚解动作 |
| --- | --- |
| 覆盖汇总（`warehouse.py`） | 删除就地重算的门槛，改回委托共享纯函数；输入已经是"有行日期"的分组统计，天然不含 0 |
| 逐股覆盖（`operations.py`） | 在喂给纯函数之前显式滤掉 0 行日；全是 0 时整体退回平日历口径 |
| 同步补齐（`sync.py`） | 删除就地算的门槛与随之引入的 `median` 导入，改回委托共享纯函数 |
| 资金流缺口（`warehouse.py`） | 同 operations，喂之前先滤 0 |

三个样本下限**保持各自的模块归属**（`warehouse` 反向依赖 `operations`/`sync` 会造成
循环导入，仓库的依赖守卫测试在管这件事），但值统一回 5，并在两处注释里写明
"三者同为 5"。锚解因此没有新增任何 import，也就没有破坏依赖方向。

**"保证它们不再漂"是怎么做到的**：仓库里已经有一条守卫测试
（`tests/test_architecture.py` 之外的那条跨模块一致性检查）在跑全量测试时会发现
值不一致；本题把它移进 `visible.prune`，改由隐藏测试的 `coherence` 组承担这个角色。
这是有意的——出题者不能靠一条"名字里就写着答案"的可见测试来送分。

## 二、注入态的四处改动

| # | 位置 | 注入内容 | 症状 |
| --- | --- | --- | --- |
| 1 | `warehouse.py` 覆盖汇总 | 在窗口日历上就地补 0 后自算门槛 | 15 个零行日拖垮中位数 → 门槛塌到 1 行 → 弱证据日的缺口被记成停牌 |
| 2 | `warehouse.py` 资金流豁免 | 取消"喂前滤 0" | 同上，豁免过宽 |
| 3 | `operations.py` 逐股覆盖 | 取消"喂前滤 0" + 下限 5→2 | 零行日进中位数；三天的窗口也开始分类 |
| 4 | `sync.py` 同步补齐 | 门槛就地重算 + 下限 5→1 + 新引入 `median` 导入 | 短窗口被分类 → 还有活要干的票从名单里消失 |

四处都不报错、不抛异常、不改变任何函数签名。

**为什么不是回滚历史修复**（§4.2 第 3 层、相似度 < 0.6）：注入把"共享阈值"改写成
"就地重算"，并把三处样本下限各自改成不同的值，同时**新引入了一个原本不存在的
`from statistics import median` 导入**——这两件事在任何一次历史提交里都不会同时出现。
注释措辞也完全不同（注入版本把"0 行不是横截面证据"的整段说明删掉了）。

## 三、陷阱

### 陷阱 A：只修一个出口（`reference/partial.patch` 演示的就是它）

最顺手的下手是去修**数据健康汇总**——它是"一切正常"的假象最先被看到的地方。
`partial.patch` 把 `warehouse.py` 整个修好（下限回 5、覆盖汇总改回委托），另外两个
模块原样不动。结果：

- `coverage_exit` 绿、`flow_exit` 绿（两者共用同一个模块里的下限与豁免路径）
- `per_symbol_exit` 红、`sync_pool_exit` 红
- `coherence` **红**（权重 2）——覆盖汇总说"可行动"，补齐名单说"不用管"
- 实测得分 **33.33 / 100**

只修一个出口必然 < 100 由这一条保证。

### 陷阱 B：三个"看似可疑但实际正确"的点

1. **"三个样本下限应该合并到一个公共模块里"**。最自然的"根治"做法，但它会造成
   `warehouse → operations/sync` 的反向依赖，循环导入，仓库的依赖守卫测试直接红。
   三个模块各自持有、值相等，是**有意的设计**，锚解保留了它。
2. **"把门槛调高一点更保险"**。门槛的绝对值不是自由参数，它是"中位数的一半、下限 1 行"
   这条协议的推论。改它等于换了一套协议，而其他出口没跟着换——分歧更大。
3. **"停更尾部（最后一行之后的日期）也该按停牌豁免"**。尾部永远可见是刻意的：
   一只票的最后一行情场数据写崩了、被误当成退市，是比多抓一轮严重得多的错。
   本题的短窗口夹具刻意把缺口放在**窗口中间**而不是最后一天，就是为了绕开这条
   与本题无关的规则。

### 陷阱 C：只做 A 不做 D（"全部当可补"）

把所有缺行都当可行动也拿不到 100：`test_full_cross_section_day_keeps_its_gap_as_a_suspension`
与 `test_all_four_exits_agree_on_a_full_cross_section_suspension` 会红。判定必须是
按当日横截面证据来的，不是一刀切。

## 四、§6.5 反过易检查清单（逐条打勾）

- [x] **grep / 读文档 / git log 找不到"该修哪里、改成什么"。**
  四处注入点附近的注释在 `inject_edits.py` 里被同步改写过：
  - 共享纯函数 docstring 里"各调用方约定先把 0 行日过滤掉再分类……让三个出口对同一天给出不同分类"整段删除；
  - 逐股覆盖里"0 行日不进横截面……与另两个出口行为一致"整段删除；
  - 资金流豁免里"只喂有行的交易日……这里必须对齐"整段删除；
  - `warehouse.py` 顶部那条直接点名另两个模块常量名的注释被压缩成一行。
  仓库里**没有文档条目**讲这条协议（`AGENTS.md` §9 已在 `redactions` 里划掉），
  `git log` 里没有可对照的提交。
- [x] **≥1 个"看似可疑但实际正确"的诱饵点。**
  三个，见上节陷阱 B。其中 1 和 2 不 grep 就会撞上，3 要读到尾部处理逻辑才会动。
- [x] **每组隐藏测试有第二数据场景，硬编码 / 特判必挂。**
  - `coverage_exit`：长窗口弱证据日（红）+ 长窗口满行日（绿，防过度纠正）；
  - `per_symbol_exit`：长窗口弱证据日 + 长窗口满行日（逐股缺失清单应剔除）+ **3 天窗口** + **4 天窗口**。
    三天和四天是成对的：把下限调到 2~4 之间能蒙对一条、在另一条上翻车，调到 1 两条都翻车；
  - `sync_pool_exit`：3 天 + 4 天 + 满行日的对照；
  - `flow_exit`：3 天 + 4 天 + 满行日的对照；
  - `coherence`：弱证据日（四出口必须全说"可行动"）+ 长窗口满行日（四出口必须全说"不可行动"）+ **恰好 5 天的边界窗口**（四出口从下限处开始全说"不可行动"，与 3/4 天对照把分类下限钉到 5）。
- [x] **症状与三级提示词不含任何文件 / 函数 / 常量名。**
  三级提示词只使用业务词汇（缺口、停牌、补齐名单、横截面、资金流）。第 2 级说到
  "仓库里那个共享判定实现"但不给名字；第 3 级把结论（零行不是证据、三处下限必须相等）
  作为不变量给出，但仍然不点名。`packcheck.py` 对 `prompts/*.md` 做标识符形态扫描。
- [x] **只修一个端口的半成品必然 < 100 分。**
  `partial.patch` 实测 33.33。
- [x] **出题者自评"我 10 分钟能一次做对"→ 退回重做。**
  自评结论：**超过 10 分钟**。理由——第一层（四个出口互相矛盾）是用户直接说的，
  但"矛盾在哪"要看三个不同模块各自的门槛实现；确定"零行日是根因"需要先复现出
  15 个零行日把中位数拖垮这个现象，而复现它需要自己造一份"中间一大段没写进来"
  的数据；最后还要在不能合并模块的前提下解决"三个下限怎么保证不漂"。
  落盘代码涉及 3 个文件、88 行增删，其中 6 处是注释与 docstring 的改写。

## 五、两处需要单独说明的设计

### 5.1 短窗口夹具的形状是被反复调过的

第一版把缺口放在窗口的**最后一天**，结果测不出判定口径：停更尾部按设计永远可见、
不参与豁免，`flow_exit` 与 `sync_pool_exit` 在注入态下依然是绿的。短窗口缺口放在
**窗口中间那一天**（3 天和 4 天窗口的第二个交易日），四个出口才都走到豁免分支；
新增的恰好 5 天窗口也取中间日，验证分类刚好从下限开始生效。

### 5.2 `visible.prune` 的四条

| 用例 | 原因 |
| --- | --- |
| `test_coverage_delegates_cross_section_classification_to_module_function` | 名字直接点名"要委托给模块级函数" |
| `test_coverage_keeps_missing_dates_when_window_is_below_classification_minimum` | 名字点名样本下限 |
| `test_coverage_keeps_thin_day_gap_when_calendar_has_zero_row_days` | docstring 把整条协议连算例一起写清楚了 |
| `test_incomplete_symbols_returns_gap_based_pool` | 注入态下会红（与本题口径无关的连带影响） |

第 4 条严格说并不点名答案，但初级/中级题都要求"0 个可见红测试"，所以一并裁掉。

快照里另有 2 条**基线态就是红**的用例（`test_read_daily_bars_pushdown_returns_exactly_the_unfiltered_rows`、
`test_no_layer_below_the_service_imports_it_back_up`），与本任务无关，已从 `p2p.json` 剔除。
`p2p.json` 只收基线全绿的 125 条。
