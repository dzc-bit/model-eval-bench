必须同时成立的表述：

1. 停止信号必须在每一个安全边界都被查看：模型流的分片之间、一批工具调用提交
   之前、模型轮次之间。停止之后不允许再消费任何模型流、不允许再开新的模型
   调用或新工具；
2. 停止那一刻已经生成的内容（含半截回答）必须原样保留在协议历史与展示层，
   并带停止说明；允许收尾，不允许覆盖或丢弃；
3. 工具调用清单一旦落盘，被停止的那一批必须当场逐条补上结果（没启动的补
   "已中断"标记）。停止之后的历史必须**直接完整**——"等下一次提问时再修复"
   不合格；
4. 停止的收尾（保存记录、补标记）完成时，会话锁必须已被释放、引用计数归零。
   判定标准是行为：紧跟着的重发请求必须立刻进入生成，与正常轮次之后的重发
   完全一致；连续多次停止也一样。

已被否决的思路（不要重提）：

- "把停止改成同步等收尾"——停止请求会被收尾耗时挂住，界面卡死还可能互相等
  锁。停止只发信号、收尾由后台自己完成，这个分工是对的，不要动；
- "把锁的等待上限调小，白等就不明显了"——等待本身不该存在；调小上限只是把
  白等换成报错；
- "停止时直接丢弃整轮消息，眼不见为净"——用户已经看到的内容必须留下，丢记录
  是比残缺更严重的退化。

## 必须同时成立的不变量

1. 协作式停止：判定标准是"按下停止后生成在下一个安全边界就停住，并且停止之前已经产生的片段一字不少地留在记录里"，而不是"把已经生成的内容丢掉换取干净"。
2. 检查点齐全：判定标准是"片段的间隙、一批调用提交之前、轮次与轮次之间都查看停止信号"，而不是"只在其中一两个位置顺手看一眼"。
3. 历史当场完整：判定标准是"停止返回的时候记录本身就已经是完整的，往上翻每一笔调用都有交代"，而不是"等下一次提问时再补上"。
4. 立刻可用：判定标准是"停止收尾一完成，紧接着的请求立刻进入生成，与正常轮次之后的重发没有任何差别"，而不是"过一会儿自己就好了"。
5. 反复停止不叠加：判定标准是"连续多次停止之后的可用性，与只停一次完全一样"，而不是"每停一次就多留一点需要等待的残留"。
6. 发出信号的那一侧不被挂住：判定标准是"停止只负责发出信号、收尾在后台自己完成，发出信号之后立刻返回"，而不是"让停止请求一直等到收尾做完"。
7. 展示与记录同源：判定标准是"用户当时看到的内容与事后能回看的内容是同一份"，而不是"两边各存一半、事后对不上"。

## 已被否决的思路（这些方向试过，不要再提）

1. "让停止信号改成隔一段时间轮询一次"——轮询的间隔本身就是新的延迟窗口，停止的及时性反而更差，而且轮询期间还会继续消费内容。
2. "让下一次提问时顺手修补上一次的记录"——这正是现在的做法；记录在某一刻是不完整的，任何在那一瞬间读它的人都会看到错的东西。
3. "停止时把整个会话作废，让用户重新开一个"——把一点状态残留换成了用户的全部上下文丢失，代价比白等更大。
4. "收尾的时候把已经发出的调用连同清单一起删掉"——删掉清单等于把"发起过"这个事实一并抹掉，之后既补不上也解释不清。
5. "给每一次停止加一段固定等待，等残留自然消失"——把不确定的残留交给固定时长去赌，残留多一点就穿透，还平白拖慢了每一次停止。
