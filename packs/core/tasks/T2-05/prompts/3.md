（第 3 级提示词——不变量 + 否决项）

必须同时成立的表述：

1. 准入不变量：相同签名的在途任务，任何时刻在系统里最多只能有一个在跑；判定与写入必须原子完成，并发提交必须严格互斥并复用在途记录。
2. 心跳不变量：正在推进（任何有效写回）或仍有调用方查询的任务，绝不能被判定为失活僵尸；两者满足其一即为存活。
3. 清理不变量：终态记录的生命周期必须与去重签名、取消标记同生共死；记录过期被逐出时，关联的去重索引与标记必须一并清空，不得留有幽灵残留。
4. 出口不变量：容量超限的响应必须如实反映当前在途的任务集合；对外查询任务状态时，复用准入这一事实必须对调用方可见。

已被否决的思路（不要重提）：

- "给每次提交加前端生成的全局唯一标识"——破坏了基于任务参数的去重契约，无法解决多入口重复提交的问题。
- "在提交入口加一段等待或延时重试以躲过并发窗口"——把竞态窗口藏进随机等待，高并发下依然必然穿透。
- "把并发容量上限调大以掩盖容量耗尽"——僵尸任务与幽灵索引未清理，名额迟早再次耗尽，不修根因。

## 必须同时成立的不变量

1. 准入互斥：判定标准是"同一批提交参数的在途任务，任何时刻在全系统至多只有一个，判定与写入是一步完成的"，而不是"先查一遍再写一遍、中间留一道缝"。
2. 名额如实：判定标准是"容量超限时返回的在跑集合与系统里真实在跑的集合逐条对得上"，而不是"只回一句已经满了、让调用方自己猜"。
3. 存活口径两选一：判定标准是"只要还有有效写回、或者还有调用方在查询，就判定为活着"，而不是"只看其中一种动静"。
4. 清理同生共死：判定标准是"终态记录被逐出时，去重依据与取消标记一并消失，逐出之后重新提交能被正常接纳"，而不是"记录清了、索引还留着"。
5. 复用事实可见：判定标准是"对外查询能明确回答本次是否复用了已提交的那一次"，而不是"这个信息在翻包时被丢掉"。
6. 失败必须给出原因：判定标准是"真正失活的任务被收走时给出明确的失败原因并释放名额"，而不是"静默消失、名额一直悬着"。
7. 并发不排队：判定标准是"并发提交要么被严格挡住、要么复用已有任务，不允许在等待队列里堆叠"，而不是"先排上队再说"。

## 已被否决的思路（这些方向试过，不要再提）

1. "等定时巡检跑完再放行新的提交"——把准入交给一个周期性的后台动作：提交要么被长时间挡住，要么在巡检的间隙里照样重复进来，互斥始终没有建立起来。
2. "让提交方在本地记一份'我已经提过了'"——本地记录跨不了进程、也跨不了入口，多个入口提交同一批活照样各跑各的。
3. "把僵尸判定改成永不触发，免得误杀"——误杀是没有了，可真正失活的任务会永久占住名额，容量提示一直亮着红灯。
4. "清理时只把状态改成终态，记录留在登记表里"——名额不会被释放，下一次提交仍然被判成"已经有在跑的任务"，等于把泄漏留在了账上。
5. "把容量上限按入口各自分配额度"——同一批活可以从不同入口各拿一份额度，防重的前提直接失效。
