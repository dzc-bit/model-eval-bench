## 2. 缺陷逐条拆解

### A. `statusInfo()` 把 `cancelled` 渲染成"沙箱就绪"

`console/static/js/views/workspace.js:577-595`，现状：

```js
function statusInfo(s) {
  const run = s.run;
  if (!run) { ... }
  if (run.chat_busy) return { kind: 'busy', text: S.CHAT_REMOTE_BUSY };        // 583
  if (s.busy === 'grade' || run.status === 'grading') return { ... };         // 584
  if (s.busy === 'prepare' || run.status === 'preparing') return { ... };      // 585
  if (run.status === 'queued') return { kind: 'busy', text: S.RUN_STATUS_QUEUED };  // 586
  if (run.status === 'error') return { kind: 'error', text: S.RUN_STATUS_ERROR };    // 587
  if (s.modelMismatch) return { ... };                                          // 588
  if (run.revealed || s.revealed) return { ... };                               // 589
  if (run.status === 'graded') { ... }                                          // 590
  return { kind: 'ok', text: S.RUN_STATUS_READY };                              // 594  ← 落在这里
}
```

`error` 有分支（587），`cancelled` 没有，一路落到 594 返回 `{ kind: 'ok' }`——一个"一切正常"的绿色状态。

配套问题：`console/static/js/core/strings.js:120-126` 的词表注释写着
"与后端 `runs.run_view` 的 status 取值一一对应"，但里面**没有 `cancelled` 这一项**。

**建议**：加 `RUN_STATUS_CANCELLED`，并在 `statusInfo()` 里给它一个终态分支（`kind: 'warn'`），
文案要说清两件事——这一轮已经结束、成绩评不了了。把 `strings.js:120` 那条注释一并对齐，
或者按现有惯例在 `workspace.js` 的本地 `T` 常量里加（该文件第 78 行注释说"strings.js 本轮冻结，新增一律走本地常量"）。

顺带核一遍：还有哪些 `status` 取值在这两个函数里没有分支。
`runs.run_view`（`console/harness/runs.py:1046`）下发的是 `run.get("status", "unknown")`，
合法取值见 `runs.py` 与 `batch.py`：`queued / preparing / ready / grading / graded / error / cancelled`。

### B. 主按钮是个点了必报错的死按钮

`workspace.js:378-380`，现状：

```js
if (run.status === 'error' || run.status === 'cancelled') {
  return { label: T.P_REBUILD, onClick: () => doRebuild(), disabled: localBusy, reason: localBusy ? T.P_LOCAL_BUSY : '' };
}
```

`disabled` 只看本地 `s.busy`，所以按钮可点、也不给任何原因。

但后端 `runs.rebuild_sandbox`（`console/harness/runs.py:347-381`）在 366-367 行：

```python
if run.get("cancel_requested") or run.get("status") == "cancelled":
    raise errors.HarnessError(errors.E_RUN_CANCELLED, "这一轮已被批次取消，不能重建沙箱。", target_id)
```

同一个 `cancel_requested` 守卫还出现在：

- `runs.reset_sandbox` — `runs.py:311-312`
- `runs.reopen` — `runs.py:590-595`
- `runs.start_grade` — `runs.py:858-863`

**这违反 AGENTS.md 的前端红线**："出口不许条件隐藏：每个状态都要把『能走的路』全摆出来；卡住时给禁用态 + 原因，不是消失。"

**建议**：`cancelled` 单独拆出来，不要和 `error` 合并。给禁用态 + 明确原因（复用 374-375 行已有的
`sandboxOk` / `sandboxReason` 判定思路），并让 ⋯ 菜单里的 `rebuild`（505-511 行）用同一套判定，
避免主按钮和菜单项各算各的。

### C. `cancel_requested` 不可撤销，被取消的记录是死路

全库检索：`cancel_requested` 只在 `console/harness/batch.py:406` 被写成 `True`，
**没有任何地方把它清回 `False`**。也就是说批次取消是不可逆的。

剩下两个出口都会毁数据：

- **「结束本轮」** → `runs.finish_round`（`runs.py:737`）→ `record_run_result`（`runs.py:677`）。
  在 692-694 行，`counted = _counted_rounds(run)` 为空就直接 `return None`，**不写台账**；
  紧接着 `purge_run` 真删整条记录（含 88 万字节的 `chat.jsonl`）。
- **「废弃本轮」** → `DELETE /api/runs/{id}`，直接全删。

也就是说 T1-01 / T1-03 这两次模型产出**既评不了分，也留不下复盘证据**。

**建议**（这一条是设计决策，请先跟他确认再动手）：

- 方案 1（保守）：只修界面（缺陷 A / B），把"这轮评不了了"说清楚，把死路标成死路。实现成本最低，
  但数据照样丢。
- 方案 2：给 `cancelled` 开一条真正的出路——比如允许对已取消的记录**重新备沙箱**（新建 run，
  旧记录保留为证据），或者提供"撤销取消"把 `cancel_requested` 清掉（**注意：此时沙箱目录已经
  被 `sandbox.destroy` 删了，清掉标志也救不回工作区**，所以这条必须配合重建沙箱才有意义）。
- 方案 3：批次取消时**不回收**工作区，等 run 真正终结（结束/废弃）时再回收。代价是占着并发槽位，
  和 `batch.py:680` 那句"把位置让给还没跑的条目"的初衷冲突，需要他拍板。

无论选哪个，AGENTS.md 都要求**出口不许条件隐藏**——现在的状态是"唯一出口会毁数据但不告诉你"。

### D. 批次回收沙箱绕过了所有在飞闸门（竞态）

**这条是在排查 A/B/C 时顺带发现的独立 bug，比 A/B/C 更值得优先修**——
T1-01 / T1-03 只是被误伤，下面这个是真的在删模型脚下正在写的文件。

证据：`runs/T2-04/cbcn-deepseek-v4.1-flash/20261002-160010/chat.jsonl` 的 mtime 是 **16:07**，
比沙箱回收（16:06:02）晚了一分钟；而 `sandboxes/T2-04__cbcn-deepseek-v4.1-flash__20261002-160010/`
目录至今还在，里面只剩模型写的两个脚本 `_scan4.py` 和 `_verify.py`——工作区主体被删了，
这两个文件是残留（`sandbox.destroy` 走 `util.remove_tree`，见 `sandbox.py:772-783`）。

根因在 `console/harness/batch.py:679-697`：

```python
def _release_item_sandbox(cfg: dict, batch: dict, run: dict, emit) -> None:
    if not batch.get("auto_release"):
        return
    try:
        latest = runs.get_run(cfg, run["run_id"])
        sandbox.destroy(cfg, latest, log=lambda m: None)   # ← 直接调 destroy
        latest["sandbox"] = ""
        ...
```

它**绕过了 `runs.release_sandbox`**，直接调 `sandbox.destroy`。而 `runs.release_sandbox`
（`runs.py:648-670`）本来是有闸门的：

```python
with chat.exclusive(run_id, blocking=False) as acquired:   # 655
    if not acquired:
        raise errors.HarnessError(errors.E_RUN_BUSY, "模型或评分正在使用这一轮，等它结束再回收沙箱。", run_id)
    run = get_run(cfg, run_id)
    if run.get("status") in {"preparing", "grading"}:     # 660
        raise errors.HarnessError(errors.E_RUN_BUSY, ...)
```

两处缺口：

1. `chat.exclusive` 是 **run 级 `RLock`**（`console/harness/chat.py:93-105`），
   而"对话在飞"是另一个计数器 `_ACTIVE_SENDS`（`chat.py:48-49`，增减在 `chat.py:1212-1222`），
   查询接口是 `chat.send_active(run_id)`（`chat.py:1237-1241`）。
   **前者不覆盖后者**，所以拿 `exclusive` 当"没人在用"的判据是漏的。
2. `_release_item_sandbox` 连 `exclusive` 都没拿。

调用点有五处，全部无保护：`batch.py:559 / 582 / 622 / 631 / 659`。
其中 626-633 是取消路径（`_mark_item_cancelled` 之后立刻回收），657-660 是 `finally` 兜底。

**建议**：

- `runs.release_sandbox` 的闸门加上 `chat.send_active(run_id)` 判断，
  在飞时抛 `E_RUN_BUSY` 或直接返回 `{"released": False, ...}` 并说明原因。
- `_release_item_sandbox` 改成走 `runs.release_sandbox`，不要自己调 `sandbox.destroy`——
  两份实现必然漂移，这跟 AGENTS.md 里记的 `packgate.py` / `selfgrade.apply_patch` 是同一类病。
- 顺带扫一遍：还有没有别的地方绕过 `runs.*` 的门面直接调 `sandbox.destroy`。

## 3. 执行者须知：硬约束

以下全部来自 `AGENTS.md`，动手前先读一遍那份文件，这里只列最容易踩的：

1. **验证门禁三条全绿才算完**：

   ```bash
   EVAL_PYTEST_TMP=D:/tmp/evalpytest-<全新目录> python -m pytest console/harness/tests -q
   python console/harness/selfcheck.py          # 必须 0 错误 0 提示
   # 每个前端模块复制成 .mjs 后 node --check（当前 42 个）
   ```

   `EVAL_PYTEST_TMP` 必须是**全新**目录，跑完删掉。残留的 `.pytest-tmp` 会让 fixture 大面积 ERROR，
   那是环境问题不是代码问题。

2. **`node --check` 对 ESM 语法静默返回 0**，等于没查。必须复制成 `.mjs` 或用
   `node --input-type=module --check` 重跑。别人 PR 描述里"全部 JS 通过 node --check"不能采信。

3. **静态声明与单测不算验收。** UI 行为要在浏览器里点一遍并读证据
   （`evaluate_script` + `getBoundingClientRect`；Browser 面板没打开时 click/screenshot 会失败）。
   这次改的正好是"按钮为什么点不动"，必须真的点。

4. **前端红线**（本次三条全踩）：

   - 出口不许条件隐藏：每个状态都要把「能走的路」全摆出来；卡住时给禁用态 + 原因，不是消失。
   - 「结束本轮」必须显式常驻。
   - 卡住的原因要**写在按钮上**，别让人去猜。

5. **测试绝不许碰真实的 `runs/` 与 `sandboxes/`。**
   `conftest.forbid_writing_real_config` 在删除函数的**入口**上挡了这两条路径。
   只 patch `config.CONFIG_PATH` **不等于**写侧落在临时目录——`config.load()` 会把
   `runs_root` / `sandbox_root` 按默认值解析到真实的 `runs/`、`sandboxes/`。
   新写删除类用例记得用 `cfg` fixture。

6. **8899 是本机唯一实例。** 重启前扫**所有** `runs/*/*/*/chat.jsonl` 的 mtime，
   最近 1–2 分钟还在写的都算在飞。`git pull` 后必须重启，否则新前端调旧后端 = "项目打不开"。
   只改 `console/static/**` 不用重启（静态文件 `no-store`）。

7. **Windows 专属**：控制台是 GBK，中文测试输出经管道会花屏（用文件读，不要 `| grep`）；
   PowerShell 一律 `pwsh` 且写 `.ps1`。

8. **不要**顺手改 `runs/` 里的记录、`sandboxes/` 的残留目录，或给台账回填东西。
   T1-01 / T1-03 这两条记录现在是取证材料，等他决定怎么处置。
