# 模型配置重构设计（对齐 DSH）

> 参考来源：本机安装的 DeepSeek Harness 源码
> （`D:\APP\DeepSeek Harness\resources\app.asar` 解包后
> `@deepseek-ai/dsh-llm-pi-ai/README.md`，以及 `~/.dsh/settings.yaml.imported` 的真实配置）。
> 本文只记「DSH 怎么做 + 我们怎么落地」，不复述它的全部能力。

## 一、DSH 的设计（一手观察）

真实配置长这样（`~/.dsh/settings.yaml.imported` 脱敏）：

```yaml
llm-pi-ai:
  providers:
    wangwang:                        # provider 名 = 请求时选路由用的 key
      displayName: 汪汪Gemini
      apiKeyEnv: WANGWANG_API_KEY    # 密钥「引用」，不落盘
      api: openai-completions        # 协议
      baseURL: https://api.hyhawang.com
      models:                        # ← 供应商下挂多个模型
        - id: gemini-3.6-flash
          name: gemini-3.6-flash
agent-default-model:
  provider: agy                      # 引用方式：{provider, model} 成对
  model: gemini-3.6-flash-high
```

字段全集（`dsh-llm-pi-ai/README.md` 的字段表）：

| 层级 | 字段 | 含义 |
| --- | --- | --- |
| provider | `displayName` | 选择器展示名 |
| provider | `apiKeyEnv` | 凭据引用，逐请求解析；缺省则交给环境发现 |
| provider | `api` | 线协议；仅目录未描述的路由需要 |
| provider | `baseURL` | 该路由下**所有**模型的端点 |
| provider | `models` | 模型清单；**整体替换**目录而非追加 |
| provider | `modelOverrides` | 只改造目录里的个别模型，保留其余 |
| provider | `defaultContextWindow` | 未描述模型的容量兜底（默认 262,144） |
| provider | `defaultMaxTokens` | 输出上限兜底（默认 32,768） |
| provider | `retryPolicy` | 重试策略 |
| model | `id` / `name` | 请求 id / 展示名 |
| model | `contextWindow` | 逐模型容量 |
| model | `reasoningEfforts` | 可选思考档位（键=档位名，值=线上拼写） |

### 四条值得抄的设计原则

1. **provider 与 model 分层**：端点、协议、凭据属于 provider；容量、输出上限属于 model。
   同一个 provider 下加模型不需要重复填 base_url。
2. **容量有兜底链**：逐模型 `contextWindow` 优先 → provider 的 `defaultContextWindow` →
   都没有就不声明容量。输出上限同理。
3. **密钥只存引用**：配置里写的是 `apiKeyEnv`（一个名字），真实密钥在 credential store。
   配置可以随便分享，不含秘密。
4. **发现与容量解耦**：`GET {baseURL}/models` 拉到的候选带容量元数据，
   **只作为可采纳的建议**，不自动落盘——「什么被服务」始终由配置决定。

### 明确不抄的部分

- `compat`（各家线协议的兼容开关）、`requestImage*`（图像预算）、`vllmPriority`、
  模板参数——本项目只跑 OpenAI 兼容 + Anthropic 两种协议，不需要这层适配面。
- `reasoningEfforts` 的「档位改名」能力——评测台不做思考档位选择，先留字段不暴露 UI。

## 二、本项目的落地方案

### 配置结构（config.json）

```jsonc
{
  "providers": [
    {
      "id": "cbcn",                          // 路由名（唯一）
      "display_name": "cbcn 中转",           // 展示名
      "api": "openai",                       // 协议：openai | anthropic
      "api_mode": "chat_completions",        // openai 下细分：chat_completions | responses
      "base_url": "http://127.0.0.1:20128/v1",
      "default_context_window": 262144,      // 兜底容量（可省）
      "default_max_tokens": 32768,           // 兜底输出上限（可省）
      "note": "",
      "models": [
        {
          "id": "cbcn/hy4-preview",          // 请求时填的模型名
          "name": "混元 4 预览",              // 展示名（可省，省了用 id）
          "context_window": 128000,          // 可省 → 继承 provider 兜底
          "max_tokens": 16384,               // 可省 → 继承 provider 兜底
          "note": ""
        }
      ]
    }
  ]
}
```

**密钥**：按 provider 存（`keyring` 的 key 从 model_id 改成 provider_id）。
一个供应商一把密钥——这符合实际（同一中转站的多个模型共用一把 key）。

### 去掉的字段

| 字段 | 为什么去掉 |
| --- | --- |
| `key_env` | 你说的「莫名其妙」——本机密钥文件已经能存密钥了，这个环境变量名是上一版的历史包袱，两套机制并存只会让人不知道该填哪个 |
| 每个模型重复的 `base_url` / `protocol` / `api_mode` | 上提到 provider 层 |

### 「run 记录里的 model 字段」怎么办

现状：`runs/<task>/<model>/<ts>/` 的目录名和 `run["model"]` 用的是**档案 id**。
重构后 provider 下有多个模型，run 绑定的应该是**具体模型**而不是 provider。

**决定**：`run["model"]` 改为 `"<provider_id>/<model_id>"` 形态的**限定名**，
目录名沿用（`util.sanitize_id` 会把 `/` 换成 `-`）。
历史 run 的 `model` 字段是裸 id，读取时按「老档案 id」回退匹配，不做数据迁移——
`runs/` 里是评测产物，动它有风险且没必要。

### 前端（模型档案页）

从「一张卡一个模型」改成**「一张卡一个供应商，卡内列出模型」**：

```
┌─ cbcn 中转 · OpenAI 兼容 · ✓ 已存密钥 ────────── [测试连接] [编辑] [删除] ─┐
│  http://127.0.0.1:20128/v1                                              │
│  ┌──────────────────────────────────────────────────────────────────┐  │
│  │ 混元 4 预览   cbcn/hy4-preview    上下文 128k · 输出 16k         │  │
│  │ DeepSeek V4   cbcn/deepseek-v4.1  上下文 256k · 输出 32k（默认） │  │
│  └──────────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────────┘
```

编辑弹窗分两段：**供应商信息**（展示名/端点/协议/密钥/默认容量）+ **模型清单**
（可增删的行，每行 id / 展示名 / 上下文 / 输出上限）。
另加「从端点拉取模型」按钮：调 `GET {base_url}/models`，把候选列出来供勾选采纳。

### 后端改动清单

| 文件 | 改动 |
| --- | --- |
| `config.py` | 新增 `providers` 读取与归一（含老 `models` 结构的自动迁移） |
| `runs.py` | `list_models` / `upsert_model` / `delete_model` 改为 provider 粒度；新增 `discover_models` |
| `chat.py` | `_model_key` / `key_candidates` 按 provider 解析；`send` 接收限定模型名 |
| `keyring.py` | key 从 model_id 改成 provider_id |
| `server.py` | 路由表：`/api/models` → `/api/providers`；新增 `/api/providers/discover` |

### 迁移策略

读 config.json 时，如果发现是老的 `models: [...]` 平铺结构：
按 `base_url` 分组，同 `base_url` 的合并成一个 provider，`id` 取域名或首个档案 id。
迁移只在内存里做（读时转换），**不自动改写用户的 config.json**——
改写别人的配置文件风险太高，改为在界面上提示「已按端点合并，保存后生效」。

## 三、验收清单

- [ ] 一个供应商下挂多个模型，共享 base_url / 密钥
- [ ] 模型可配 `context_window` / `max_tokens`，留空继承 provider 兜底
- [ ] 密钥按供应商存，`key_env` 字段彻底消失
- [ ] 「从端点拉取模型」能列出候选并勾选采纳
- [ ] 老 config.json 能正常读取（自动分组），界面有迁移提示
- [ ] 历史 run 记录仍可读（裸 model id 回退匹配）
- [ ] 8 个视图回归无异常
